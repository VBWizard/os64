# RTL8125.md — the wire to the P5, designed before line one

*2026-08-16. The design conversation for the P5's NIC driver and the file
transfer that retires the sneakernet. Recorded by Fable before the writing;
Opus implements; nothing merges without Fable's review. Decisions marked
RATIFIED were Chris's rulings from the day's conversation; decisions marked
OPEN are his to make before (or as) the work starts. The MALLOC.md
precedent applies: this doc exists so the thinking survives whoever is in
the chair.*

## The mission, in one sentence

`os64 refresh` without a thumb drive: the P5 fetches freshly built files
from the build PC over one gigabit switch, and the sneakernet retires with
full honors.

## RATIFIED (Chris, 2026-08-16)

1. **The topology.** PC and P5 on the gigabit switch, isolated build
   segment, no gateway, no DHCP ceremony. PC = `192.168.44.1/24`
   (set in Windows: prefix length **24**). P5 = `192.168.44.2/24` via the
   kernel cmdline the stack already honors: `IP=192.168.44.2
   MASK=255.255.255.0`. The home LAN is 10.0.0.x, so no collision.
2. **The PC originates the bytes, the P5 receives them.** (See the OPEN
   direction ruling below for the twist physics adds to this.)
3. **Labor division:** design Fable's, implementation Opus's, review
   Fable's, bare-metal boots Chris's.

## THE PIVOTAL FACT the tree just disclosed

**os64's TCP has no passive open.** tcp.c implements active connections
only — `net_dial` is the entire connection-making API, and there is no
listen/accept anywhere in the stack or the syscall table. Two consequences:

- "PC pushes to a P5 listener" requires BUILDING TCP listen + accept + a
  new syscall surface first — a real arc of its own.
- "P5 *dials out* and pulls" works on the stack **exactly as it exists
  today**. Zero stack changes, zero new syscalls.

### OPEN #1 — the direction ruling (recommendation: P5 PULLS, v1)

The ratified spirit was "PC originates, P5 receives," and a pull preserves
exactly that: the PC holds the files and serves them; the P5 asks. What
changes is only who says the first word on the wire. The pull also
dissolves the WSL2 NAT question — the listener runs on the WINDOWS side of
the build PC (one `python` one-liner, below), plainly reachable at
192.168.44.1, and WSL2/portproxy/mirrored-mode never enters the story.

`listen()` for os64 is NOT abandoned by this — it is the prerequisite for
every future server this OS ever runs, and it goes to DEBTS as its own
named candy. It just isn't the toll booth the sneakernet's retirement has
to pay at.

## The protocol: `os64get`, v1 — deliberately 1971-shaped

One TCP connection per file, ASCII where a human might read it, length and
checksum where a machine must. FTP's spirit without FTP's two-socket
baroque.

```
client → server:   GET <filename>\n
server → client:   OK <length-decimal> <crc32-hex8>\n   then <length> raw bytes
              or:  NO <reason>\n
```

- **Port: OPEN #2** — recommendation `6464` (the obvious spelling).
- Filename: one path component, no slashes accepted by the server (the
  serving directory is the namespace — no traversal, no cleverness).
- Client verifies length AND CRC32 before the file is written to its final
  name; a failed transfer must leave no partial file where a good one was
  (write to `<name>.part`, rename on success — ext2 root is writable and
  rename is atomic enough for a two-node LAN).
- CRC32: the standard reflected 0xEDB88320 bitwise form, ~15 lines, lives
  in libos64 (`os64_crc32`) because the next consumer is inevitable.
- **The userland face:** `/bin/os64get <host> <file> [dest]` — os64_dial,
  the exchange above, progress on the glass, exit 0/1 honestly. `dest`
  defaults to the current directory (**OPEN #4** if Chris prefers /bin).

### The PC side (not os64's code, but the doc records it)

A ~30-line Python listener on the WINDOWS side (not WSL2 — NAT stays out
of the story), serving exactly one directory, e.g. the build's
`userland/bin` mirror. `GET`, whitelist check, `OK len crc`, bytes, close.
Chris runs it when refreshing; it is not a daemon, it is a valet.

## The driver: r8125, v1

**Identity:** PCI vendor:device `10ec:8125`. MMIO registers via BAR
(memory BAR — map `PAGE_PCD` like every device, xhci.c precedent). The
P5's NIC was identified in the sysfs arc: RTL8125 2.5GbE, running at
1000BASE-T against the ratified gigabit switch (2.5G silicon treats
gigabit as a comfortable second gear).

**Family shape** (the part that makes this a weekend, not a winter): the
8125 is the RealTek descriptor-ring lineage — TX and RX rings of 16-byte
descriptors (`opts1` = OWN bit + flags + length, `opts2`, 64-bit buffer
address), 256-byte ring alignment, first/last-segment bits per descriptor,
device owns the descriptor while OWN=1. Allocate rings + buffers with
`kmalloc_aligned` (zeroed, contiguous, HHDM-addressed — the DMA discipline
xhci.c documents). One RX buffer per descriptor at 2KB covers standard
MTU; no jumbo frames in v1.

**⚠️ REGISTER-OFFSET TRIPWIRE — read before trusting anything below.**
This doc's author knows the FAMILY architecture cold and the 8125's exact
register map only approximately; the 8125 moved and widened several
registers relative to its 8168 ancestors (notably interrupt mask/status,
which are 32-bit and relocated, and the PHY access which goes through OCP
registers rather than the classic PHYAR dance). **Opus must verify every
register offset against an authoritative source — the vendor's GPL r8125
driver or Linux's r8169.c (8125 = RTL_GIGA_MAC_VER_60+) — and record in
the driver's comments WHICH source each offset came from.** A plausible
offset from this doc's memory is exactly the "stale comment hiding a real
bug" fingerprint this house already paid for once. Trust the shape;
verify the numbers.

**Bring-up sequence (the shape, offsets per the tripwire above):**
1. PCI: enable memory space + bus mastering — LIVE read-modify-write of
   the command register, never the enum cache (the ruling from a848273).
2. Soft reset via ChipCmd; wait for the bit to clear.
3. Unlock config registers (9346CR magic), set MAC if needed (read MAC0/4
   for the burned-in address — the stack wants it for net_device_t).
4. Program TX/RX descriptor base addresses (low/high), RX config (accept
   broadcast + our MAC; promiscuous OFF), TX config, max RX size.
5. Enable TX/RX in ChipCmd. Leave ALL interrupts masked — v1 polls.
6. Link: poll PHY status for link-up at init with a bounded wait and an
   honest serial line either way ("r8125: link 1000/full" / "r8125: no
   link — is the cable in?").

**RX/TX, polled (OPEN #3 resolved by precedent — see below):** a
`r8125_poll()` walking RX descriptors while the device has surrendered
OWN, handing frames to the registered `net_rx_handler_t`, refilling and
re-arming OWN; TX writes the descriptor, sets OWN, rings the TX doorbell
register, and reaps completions on later polls. Hooked into the same
polling cadence virtio_net_poll and xhci_poll already ride.

### Interrupts — RULED-shaped after the fact-check (2026-08-16, second pass)

The facts the tree supplied when Chris asked "why not MSI-X?":

- **MSI-X does not exist in os64.** e1000.c defers it by name ("the day
  MSI-X wants doing properly... the RTL8125 on the P5") because the
  82540EM, a 2002 PCI part, has no MSI-X capability. The plumbing — PCI
  capability walk, table BAR mapping, per-vector allocation honoring the
  AP TPR ≥0x40 rule — is UNBUILT infrastructure whose inaugural customer
  would be this chip. Its own arc, booked, not this one.
- **What exists:** INTx with a minimal top/bottom split — the ISR sets a
  RxWork doorbell, processSignals drains. GSI probing with storm defense,
  certified on two hypervisors, never yet on bare metal. "Stage 2" is the
  grown-up deferred-work subsystem that would replace the processSignals
  piggyback; it was sequencing advice, not architecture, and e1000
  shipped without it.

**The plan: PHASED, one arc.** First light runs POLLED — on hardware no
emulator can rehearse, one unknown at a time: prove the silicon moves
frames before asking whether an interrupt routes. Once a GET has
completed end-to-end, port the e1000 INTx pattern (probe, storm defense,
doorbell flag) within the same arc — mechanical, battle-tested code
meeting its first bare metal. A `POLL8125` cmdline flag keeps polling as
the flashlight fallback forever, SCHED=periodic-style. MSI-X and Stage 2
both stay booked, unhostaged, with this driver as their named future
customer.

## The testing reality (auto-mode, read this twice)

**QEMU does not emulate an RTL8125.** There is no harness boot where this
driver meets its silicon. Therefore, three tiers, honestly divided:

1. **Host unit tests — Opus's auto-loop CAN run these.** The descriptor
   protocol is pure memory manipulation: `tools/test_r8125_host.c` in the
   test_heap_host mold, faking the MMIO surface with a struct and
   asserting ring arithmetic — OWN-bit lifecycle, wrap, first/last
   segmentation, refill, "device" completing TX out of order. The CRC32
   and the os64get protocol parser (feed it `OK`/`NO`/truncated/corrupt
   streams) are host-testable to death. Most of the BUGS this arc can
   have live exactly here, so this is where the tests live too.
2. **QEMU regression — auto-loop CAN run this.** The driver must probe
   absent hardware and stand down silently: e1000/virtio boots stay 22/22
   green with r8125 code merely present. No new fixture needed; the
   existing roster is the assertion.
3. **Bare metal — CHRIS-gated, not automatable.** First light on the P5:
   DEBUG_NET flashlight plus staged serial beacons — probe found it, MAC
   read, link negotiated, first RX frame, first completed GET. Auto mode
   ends at the P5's power button, and the afternoon plan should expect
   commits to pause there until a human boots.

## Integration notes for the implementer

- Register a `net_device_t` with a `transmit` op; the existing stack does
  ARP/IPv4/TCP above it unchanged. Zero stack modifications in this arc.
- `nor8125` cmdline flag, sibling of `noahci`/`nonvme` — the flashlight
  convention.
- All-allocations-zeroed doctrine stands: no redundant memsets after
  kmalloc_aligned; never flag them.
- stdint names; generous comments stating intent; every deferred item
  (INTx, listen(), jumbo, multi-file sessions, resume, 2.5G against a
  future switch) gets a DEBTS row at write time, not at review time.

## AMENDMENT — the implementer's fact-check (Opus, 2026-08-16 afternoon)

*Fable asked for verification before line one, which is the point of
writing a design down. Everything above survived except where noted. The
claims about what EXISTS were checked against the tree, one at a time.*

### Confirmed true (the load-bearing ones)

- **"os64's TCP has no passive open"** — the pivotal fact holds. `tcp.h`
  says ACTIVE OPEN ONLY in its own V1 SCOPE; `TCP_LISTEN` and
  `TCP_SYN_RECEIVED` exist as enum placeholders and nothing else; there is
  no `listen`/`accept` in the kernel or the syscall table. The pull
  direction is therefore free and the push direction is an arc.
- **`IP=`/`MASK=` work, and `IP=` suppresses DHCP** (`kernel.c:322`). No
  `GW=` is needed for a same-subnet peer — `ipv4.c:222` routes on-link by
  netmask, so the bogus default gateway is never consulted. There is
  already a precedent boot entry doing this shape (`limine.conf`, the TAP
  net entry).
- **Zero stack changes.** `net_device_t` + a `transmit` op is the whole
  driver contract.
- **Every e1000 INTx claim** — vector 0x45, the GSI 16–23 probe sweep, both
  storm breakers, the `kE1000RxWork` doorbell consumed in processSignals,
  the `kE1000IntxDivorced` receipt.
- **MSI-X genuinely does not exist** — no capability walk, no vector
  allocator anywhere. virtio explicitly writes `VIRTIO_MSI_NO_VECTOR`.
- **QEMU has no RTL8125 model**, so the three-tier testing reality stands
  exactly as written.

### Corrections

1. **`nor8125` must be `NOR8125`** (and `POLL8125`). The cmdline parser
   matches with `strcmp` and never folds case. This is not pedantry: the
   same sweep found three boot entries passing tokens that matched nothing
   — `noahci`, `nonvme`, and `noseriallog` — two now fixed and one booked
   (commit 642eb9f). Also note the real precedent for NICs is a single
   `NONET`; there is no per-NIC off switch today, so `NOR8125` establishes
   one.
2. **"handing frames to the registered `net_rx_handler_t`"** — drivers must
   call `net_device_rx()`, never the handler. `net_device.h:126` is
   explicit ("never directly to the stack"), and that indirection is where
   the counters and the future kworker queue live. e1000_poll does it
   right; copy that, not the sentence.
3. **The MMIO BAR is BAR2, not BAR0.** On the 8169/8125 family BAR0 is I/O
   space (Linux's r8169 uses `region = 2`). e1000.c hardcodes BAR0, so a
   copy-paste of `e1000_bar_phys(dev, 0)` returns 0 here — it fails loudly,
   which is something, but name the number and skip the hour.
4. **Ring allocation: either is fine, but know why.** The doc says
   `kmalloc_aligned`; both NIC precedents use `allocate_memory_aligned` and
   e1000.c:609 documents the reasoning. Checked: `kmalloc_aligned`
   (kmalloc.c:24) IS `allocate_memory_aligned` plus HHDM plus bookkeeping,
   so it is page-aligned and physically contiguous and works. The actual
   trap the doc correctly avoids is `kmalloc_dma`, which identity-maps.
5. **`rename` did not exist** when this was written, so the doc's
   "write to `<name>.part`, rename on success" described a call the tree
   did not have — no syscall, no ext2 implementation, only a vestigial
   Linux-shaped slot in `vfs_inode_operations` that nothing filled. BUILT
   AND SHIPPED FIRST (syscall 43, commit 8b78ff0, atomic replace ruled by
   Chris), precisely so this recipe is real by the time os64get needs it.

### Two things the bring-up sequence does not name, and should

6. **The INTx port is NOT mechanical.** e1000's GSI probe works because
   the chip can FIRE ITS OWN INTERRUPT ON COMMAND — `e1000.c:1060` writes
   `ICS = LSC` and counts ISR entries. The 8169/8125 family's ISR is
   write-1-to-CLEAR; there is no equivalent worth betting a bring-up on.
   Without a self-trigger the probe needs a different confirmation event
   (link-change on cable insertion, or a real arriving frame). Phase 2 is
   therefore "port the pattern AND invent its doorbell test," not "port
   battle-tested code." Budget accordingly.
7. **Two RTL8125 landmines.** Linux and the vendor driver load a PHY
   FIRMWARE BLOB (`rtl8125a-3.fw`, `rtl8125b-2.fw`); link usually
   negotiates without it, but it is an unnamed unknown sitting on the
   critical path. And Realtek PCIe parts are notorious for needing ASPM
   DISABLED or RX stalls appear. Both belong in the first-light beacon
   list, because neither can be debugged in a loop on hardware no emulator
   rehearses.

### The number nobody stated, and it bears on the mission

8. The transfer path is `r8125_poll → net_device_rx → tcp_input`, all
   inline in `processSignals` under `kSchedulerSwitchTasksLock` — which
   DEBTS.md already flags, naming "TCP at real speeds" as its trigger.
   `TCP_RCV_BUF` is 8KB and IS the advertised window; a scheduler pass is
   ~10ms (`MP_SCHEDULER_RUNS_PER_SECOND` is 100, despite the name). The
   ceiling is therefore roughly **window-per-pass ≈ 800 KB/s**, on a
   gigabit link. A 10MB refresh lands around 12 seconds.

   Two consequences worth having in writing:
   - **INTx does not fix this.** The doorbell only skips the poll when the
     wire is idle; the drain still happens once per pass. The doc frames
     INTx as the grown-up upgrade — for latency-when-idle it is, for
     throughput it is not.
   - The cheap levers are `TCP_RCV_BUF` and RX ring depth, not interrupts.

   Chris's ruling (2026-08-16): connectivity first, and
   "better-than-a-1990s-modem" is the bar. 800 KB/s clears it by a factor
   of several hundred. Document the number, measure it on first light,
   optimize only if the evening allows.

### One more argument FOR the pull ruling than the doc gives

TCP's SEND path is stop-and-wait — one unacknowledged segment at a time
(`tcp.h`, V1 SCOPE). The RECEIVE path is a real buffered stream. So a P5
that pulls uses the good half of the stack, while a PC push would have
shoved megabytes through stop-and-wait. The ruling was right for reasons
beyond who speaks first. (Out-of-order arrivals are dropped, incidentally
— harmless on a two-node switched LAN with nothing to reorder them.)

### Precedent the doc does not cite

`userland/apps/fetchtest/` is already os64get's exact shape: dial TCP,
write a request, read a stream to EOF, honest named exit codes, with a
comment saying outright that the real utility is Chris's to write. Start
there, not from scratch. `dialtest` sits beside it.

### Housekeeping

- **The segment moved, 2026-08-16.** Ruling #1 above says `192.168.44.0/24`
  (PC `.1`, P5 `.2`). What Chris actually built that evening is
  `192.168.0.0/24` — PC `192.168.0.44`, P5's Win11 `.100`, os64 `.2`. The
  ruling's REASON survives untouched (the home LAN is 10.0.0.x, so neither
  choice collides), so the doc follows the wire rather than asking the wire
  to follow the doc. This was carried by a dedicated boot entry, `/Bosgame
  Boot (r8125 net — the build segment)`, until the 2026-08-20 limine.conf
  walk retired it: **the 8125 needs no token to come up** — it is probed and
  brought up like any other device, so that entry enabled nothing the
  ordinary Bosgame entries do not already do. It also went stale when ICS
  took over addressing (DHCP, not the static segment above). Any Bosgame
  entry is now the r8125 entry; add `DEBUG_NET` with `e` at the menu for the
  driver's own commentary.
- **os64 answers to `.2`, NOT to the `.100` the P5's Win11 uses**, and that
  is a testing decision rather than an aesthetic one. It is one machine and
  one NIC, so both operating systems present the SAME MAC — meaning if os64
  claimed `.100` the peer's ARP cache would already hold that mapping from
  the Windows session and would never send an ARP request at all. The ARP
  exchange is the one thing that proves os64's receive path; a stale cache
  entry would silently skip it and leave us reading a passing ping as
  evidence of something it never tested.

- The P5's NIC is **10ec:8125**, confirmed by Chris from a live lspci on
  2026-08-16. `NETWORK.md`'s hardware inventory still says "P5's inventory
  is TBD" and should be struck when this arc lands.
- `listen()` is not yet a DEBTS row. The doc promises it becomes one; it
  should, when this arc books its own.
- **Upgrade-in-place WORKS — built 2026-08-16, before the driver.** This
  bullet was written as a warning ("os64get will meet this wall") and is
  kept as a record of it being knocked down the same afternoon. A running
  program holds its ELF open for demand paging (`elf_loader.c:647`), so
  `/bin/husk` used to refuse both `unlink` and `rename`. Chris chose to pay
  it rather than route around it, and the cure is the one Unix has always
  had: the name goes at once, the inode survives nameless on ext2's on-disk
  orphan chain (`s_last_orphan`), and the storage returns at last close — or
  at the next mount, which announces what a crash left behind. So os64get
  may write straight over a binary that is running; the running copy keeps
  demand-paging its own image, and the new one is there after the reboot
  the refresh ends with anyway. Verified end to end, including a hard power
  cut mid-window (VERIFICATION.md). One landmine fell out of it and is
  BOOKED, not blocking: `kmalloc_dma`'s identity mapping exists only in
  kKernelPML4, so disk I/O from any other address space faults — irrelevant
  to this driver, whose rings and BAR are HHDM-addressed like every NIC
  here, but worth knowing before adding disk work in a novel context.
