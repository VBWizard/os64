## The mission, in one sentence

`os64 refresh` without a thumb drive: the P5 fetches freshly built files
from the build PC over one gigabit switch, and the sneakernet retires with
full honors.

## RATIFIED (Chris, 2026-08-16)

1. **The topology.** PC and P5 on the gigabit switch, isolated build
   segment, no gateway, no DHCP ceremony. PC = `192.168.44.1/24`
   (set in Windows: prefix length **24**). P5 = `192.168.44.2/24` via the
   kernel cmdline the stack already honors: `IP=192.168.44.2
   MASK=255.255.255.0`. The home LAN is 10.0.0.x, so no collision.
2. **The PC originates the bytes, the P5 receives them.** (See the OPEN
   direction ruling below for the twist physics adds to this.)
3. **Labor division:** design Fable's, implementation Opus's, review
   Fable's, bare-metal boots Chris's.

## THE PIVOTAL FACT the tree just disclosed

**os64's TCP has no passive open.** tcp.c implements active connections
only — `net_dial` is the entire connection-making API, and there is no
listen/accept anywhere in the stack or the syscall table. Two consequences:

- "PC pushes to a P5 listener" requires BUILDING TCP listen + accept + a
  new syscall surface first — a real arc of its own.
- "P5 *dials out* and pulls" works on the stack **exactly as it exists
  today**. Zero stack changes, zero new syscalls.

### OPEN #1 — the direction ruling (recommendation: P5 PULLS, v1)

The ratified spirit was "PC originates, P5 receives," and a pull preserves
exactly that: the PC holds the files and serves them; the P5 asks. What
changes is only who says the first word on the wire. The pull also
dissolves the WSL2 NAT question — the listener runs on the WINDOWS side of
the build PC (one `python` one-liner, below), plainly reachable at
192.168.44.1, and WSL2/portproxy/mirrored-mode never enters the story.

`listen()` for os64 is NOT abandoned by this — it is the prerequisite for
every future server this OS ever runs, and it goes to DEBTS as its own
named candy. It just isn't the toll booth the sneakernet's retirement has
to pay at.

## The protocol: `os64get`, v1 — deliberately 1971-shaped

One TCP connection per file, ASCII where a human might read it, length and
checksum where a machine must. FTP's spirit without FTP's two-socket
baroque.

```
client → server:   GET <filename>\n
server → client:   OK <length-decimal> <crc32-hex8>\n   then <length> raw bytes
              or:  NO <reason>\n
```

- **Port: OPEN #2** — recommendation `6464` (the obvious spelling).
- Filename: one path component, no slashes accepted by the server (the
  serving directory is the namespace — no traversal, no cleverness).
- Client verifies length AND CRC32 before the file is written to its final
  name; a failed transfer must leave no partial file where a good one was
  (write to `<name>.part`, rename on success — ext2 root is writable and
  rename is atomic enough for a two-node LAN).
- CRC32: the standard reflected 0xEDB88320 bitwise form, ~15 lines, lives
  in libos64 (`os64_crc32`) because the next consumer is inevitable.
- **The userland face:** `/bin/os64get <host> <file> [dest]` — os64_dial,
  the exchange above, progress on the glass, exit 0/1 honestly. `dest`
  defaults to the current directory (**OPEN #4** if Chris prefers /bin).

### The PC side (not os64's code, but the doc records it)

A ~30-line Python listener on the WINDOWS side (not WSL2 — NAT stays out
of the story), serving exactly one directory, e.g. the build's
`userland/bin` mirror. `GET`, whitelist check, `OK len crc`, bytes, close.
Chris runs it when refreshing; it is not a daemon, it is a valet.

## The driver: r8125, v1

**Identity:** PCI vendor:device `10ec:8125`. MMIO registers via BAR
(memory BAR — map `PAGE_PCD` like every device, xhci.c precedent). The
P5's NIC was identified in the sysfs arc: RTL8125 2.5GbE, running at
1000BASE-T against the ratified gigabit switch (2.5G silicon treats
gigabit as a comfortable second gear).

**Family shape** (the part that makes this a weekend, not a winter): the
8125 is the RealTek descriptor-ring lineage — TX and RX rings of 16-byte
descriptors (`opts1` = OWN bit + flags + length, `opts2`, 64-bit buffer
address), 256-byte ring alignment, first/last-segment bits per descriptor,
device owns the descriptor while OWN=1. Allocate rings + buffers with
`kmalloc_aligned` (zeroed, contiguous, HHDM-addressed — the DMA discipline
xhci.c documents). One RX buffer per descriptor at 2KB covers standard
MTU; no jumbo frames in v1.

**⚠️ REGISTER-OFFSET TRIPWIRE — read before trusting anything below.**
This doc's author knows the FAMILY architecture cold and the 8125's exact
register map only approximately; the 8125 moved and widened several
registers relative to its 8168 ancestors (notably interrupt mask/status,
which are 32-bit and relocated, and the PHY access which goes through OCP
registers rather than the classic PHYAR dance). **Opus must verify every
register offset against an authoritative source — the vendor's GPL r8125
driver or Linux's r8169.c (8125 = RTL_GIGA_MAC_VER_60+) — and record in
the driver's comments WHICH source each offset came from.** A plausible
offset from this doc's memory is exactly the "stale comment hiding a real
bug" fingerprint this house already paid for once. Trust the shape;
verify the numbers.

**Bring-up sequence (the shape, offsets per the tripwire above):**
1. PCI: enable memory space + bus mastering — LIVE read-modify-write of
   the command register, never the enum cache (the ruling from a848273).
2. Soft reset via ChipCmd; wait for the bit to clear.
3. Unlock config registers (9346CR magic), set MAC if needed (read MAC0/4
   for the burned-in address — the stack wants it for net_device_t).
4. Program TX/RX descriptor base addresses (low/high), RX config (accept
   broadcast + our MAC; promiscuous OFF), TX config, max RX size.
5. Enable TX/RX in ChipCmd. Leave ALL interrupts masked — v1 polls.
6. Link: poll PHY status for link-up at init with a bounded wait and an
   honest serial line either way ("r8125: link 1000/full" / "r8125: no
   link — is the cable in?").

**RX/TX, polled (OPEN #3 resolved by precedent — see below):** a
`r8125_poll()` walking RX descriptors while the device has surrendered
OWN, handing frames to the registered `net_rx_handler_t`, refilling and
re-arming OWN; TX writes the descriptor, sets OWN, rings the TX doorbell
register, and reaps completions on later polls. Hooked into the same
polling cadence virtio_net_poll and xhci_poll already ride.

### Interrupts — RULED-shaped after the fact-check (2026-08-16, second pass)

The facts the tree supplied when Chris asked "why not MSI-X?":

- **MSI-X does not exist in os64.** e1000.c defers it by name ("the day
  MSI-X wants doing properly... the RTL8125 on the P5") because the
  82540EM, a 2002 PCI part, has no MSI-X capability. The plumbing — PCI
  capability walk, table BAR mapping, per-vector allocation honoring the
  AP TPR ≥0x40 rule — is UNBUILT infrastructure whose inaugural customer
  would be this chip. Its own arc, booked, not this one.
- **What exists:** INTx with a minimal top/bottom split — the ISR sets a
  RxWork doorbell, processSignals drains. GSI probing with storm defense,
  certified on two hypervisors, never yet on bare metal. "Stage 2" is the
  grown-up deferred-work subsystem that would replace the processSignals
  piggyback; it was sequencing advice, not architecture, and e1000
  shipped without it.

**The plan: PHASED, one arc.** First light runs POLLED — on hardware no
emulator can rehearse, one unknown at a time: prove the silicon moves
frames before asking whether an interrupt routes. Once a GET has
completed end-to-end, port the e1000 INTx pattern (probe, storm defense,
doorbell flag) within the same arc — mechanical, battle-tested code
meeting its first bare metal. A `POLL8125` cmdline flag keeps polling as
the flashlight fallback forever, SCHED=periodic-style. MSI-X and Stage 2
both stay booked, unhostaged, with this driver as their named future
customer.

## The testing reality (auto-mode, read this twice)

**QEMU does not emulate an RTL8125.** There is no harness boot where this
driver meets its silicon. Therefore, three tiers, honestly divided:

1. **Host unit tests — Opus's auto-loop CAN run these.** The descriptor
   protocol is pure memory manipulation: `tools/test_r8125_host.c` in the
   test_heap_host mold, faking the MMIO surface with a struct and
   asserting ring arithmetic — OWN-bit lifecycle, wrap, first/last
   segmentation, refill, "device" completing TX out of order. The CRC32
   and the os64get protocol parser (feed it `OK`/`NO`/truncated/corrupt
   streams) are host-testable to death. Most of the BUGS this arc can
   have live exactly here, so this is where the tests live too.
2. **QEMU regression — auto-loop CAN run this.** The driver must probe
   absent hardware and stand down silently: e1000/virtio boots stay 22/22
   green with r8125 code merely present. No new fixture needed; the
   existing roster is the assertion.
3. **Bare metal — CHRIS-gated, not automatable.** First light on the P5:
   DEBUG_NET flashlight plus staged serial beacons — probe found it, MAC
   read, link negotiated, first RX frame, first completed GET. Auto mode
   ends at the P5's power button, and the afternoon plan should expect
   commits to pause there until a human boots.

## Integration notes for the implementer

- Register a `net_device_t` with a `transmit` op; the existing stack does
  ARP/IPv4/TCP above it unchanged. Zero stack modifications in this arc.
- `nor8125` cmdline flag, sibling of `noahci`/`nonvme` — the flashlight
  convention.
- All-allocations-zeroed doctrine stands: no redundant memsets after
  kmalloc_aligned; never flag them.
- stdint names; generous comments stating intent; every deferred item
  (INTx, listen(), jumbo, multi-file sessions, resume, 2.5G against a
  future switch) gets a DEBTS row at write time, not at review time.
