# os64 Technical Debt Ledger

*The single sortable index of every known debt, harvested from the design
docs. Each subsystem doc remains the SOURCE OF TRUTH for its own debts (full
rationale, code sites, gotchas live there); this file is the cross-cutting
worklist you scan on a fix day to answer "what's the highest-value cheap fix
right now?" — a question no single doc can answer.*

**Maintenance rule:** when a debt is paid, delete its row here AND update the
owning section in its source doc (the two must not drift). When a review adds
a debt to a subsystem doc, add its row here too. Severity/cost are
hobby-scale judgment calls — re-rank freely.

- Severity: **Hole** (real defect exploitable/crashing) · **Robustness**
  (turns silent failures into loud ones, or prevents a known future crash) ·
  **Feature-gate** (blocks a planned feature) · **Cleanup** (honesty,
  cruft, perf-at-scale).
- Cost: **XS** (minutes) · **S** (an hour) · **M** (a session) · **L**
  (multi-session / discipline-wide).

| **Task teardown v1 SHIPPED 2026-08-06 (the graveyard shift) — residuals only.** `task_destroy()` exists: kworker buries COLLECTED corpses (retValCollected via wait/reap, autoReap by decree, or orphans) in a two-phase sweep (unlink pass N, free pass N+1 — grace period for lockless /proc walkers), freeing per-thread stacks (the 1MB+64KB per command), thread_t + TID + syscall scratch, path/cwd, static elf_image_t + its open backing file (un-haunts ext2's rm-refusal), and the task_t. **2026-08-13: three of the four residuals PAID, and the survivor is now COUNTED rather than merely admitted.** (3) page-table pages died with the paging arena (a8c952c — `arena_destroy` at burial takes the PML4 and every PDPT/PD/PT in one motion; the pool's bump allocator no longer has anything to do with a task's tables). (2) argv AND env blobs are freed — the row's own dragon warning, "env is CoW-inherited by children", was FALSE and had always been: `env_inherit` (env.c) does a plain memcpy into a fresh block and env.h says so in writing, so every task's environment is exclusively its own. | **FIXED 2026-08-13 — the graveyard race: an unlocked list append leaked whole tasks.** `task_enqueue_dead_child` was a read-modify-write on shared state with NO lock: read `parent->deadChildTail`, write `tail->deadChildNext`, store the new tail. Two siblings exiting on two cores at the same instant both read the same tail, the second's `->deadChildNext` write silently discarded the first's, and the last store won — leaving ONE child on no list at all. Not a zombie (a zombie is reachable and deliberate) but INVISIBLE: kworker's sweep only ever walks these lists, so an unlisted corpse can never be examined, collected, or buried, and every byte it owns leaks for the rest of the boot. Reproduced in `test_dynamic_linking`, which spawns two tasks that exit on the same tick on different APs and lost one of them ROUGHLY HALF THE TIME — for as long as that test has existed. The symptom was pure absence: no panic, no error, one task quietly missing from a list nobody prints. Fix: `kDeadChildLock`, one global irqsave spinlock over every deadChild list (global not per-task because the orphanage touches two parents' lists in one motion, and a per-task ordering is a deadlock waiting for its first mistake). Lock order is kDeadChildLock → scheduler queue lock, safe BY CONSTRUCTION since nothing in scheduler.c touches a deadChild list; the two calls that would have inverted it — the parent wake, and `*exitCode`'s store to a caller pointer that can fault — are deliberately performed after the release. Verified 9/9 boots clean against a ~50% pre-fix failure rate. | **IRQ0's EOI can go to the wrong controller, stranding a LAPIC ISR bit forever** (found by inspection 2026-08-10 while chasing the VBox freeze). `handler_irq0_asm` picks its EOI target by branching on `kIRQ0UsesLapic` — LAPIC if set, legacy PIC (`out 0x20`) if not. But `ioapic_adopt_isa_irq` (apic.c) sets that flag LAST: `ioapic_route_irq()` makes the redirection entry live, the PIC line is masked, and only THEN does `*uses_lapic_flag = true`. An IRQ0 delivered through the IOAPIC inside that window is acknowledged to the PIC while its LAPIC ISR bit stays set — and a set ISR bit is never cleared by anything else, so PPR pins at that vector's class for the rest of the boot, blocking every lower-priority interrupt permanently. Today the vector is 0x20 (class 2), so a stranded bit blocks almost nothing and the bug is invisible; that is exactly why it survived. It stops being invisible the moment anyone raises IRQ0's priority (see the wall-clock row) or lowers something important beneath it. Fix is one reorder — set the flag BEFORE the routing write, since a PIC EOI for an interrupt that never came is harmless while the reverse is fatal. NOTE the limit of the evidence: this does NOT by itself explain why 0x20 boots VBox cleanly and 0xE0 does not, so it is a real defect found on the way, not a proven cause of that freeze. Confirming a stranded bit needs one reading — LAPIC ISR (0x100..0x170) on a wedged guest | Hole (latent, lethal under any priority change) | XS | none — cheapest possible insurance against a whole symptom class | apic.c `ioapic_adopt_isa_irq` / handler_irq0_timer.S |

## Explicitly NOT debts (recorded so they aren't re-litigated)

- **Shared kernel upper half** (every task PML4 → kernel's own tables,
  U/S-protected): a deliberate, sound decision for os64's threat model
  (we run our own binaries). Meltdown/KPTI unshared it for a speculative
  side-channel that is out of scope. See ABI § Memory-protection.
- **The "Time to make the donuts" scheduler message**: load-bearing
  tradition, not debug noise. Never remove/reword. See SCHEDULER § donuts.
- **Pipes carry TWO copies (user→kernel ring→user), not shared memory.** The
  tempting "map one page into both tasks" optimization puts the ring's
  head/tail pointers in memory USERLAND CAN WRITE, so a buggy program could
  corrupt or hang the process on the other end. The kernel must be the arbiter
  of the buffer. (Same call GRAPHICS.md makes: syscalls carry handles, never
  pixels.) A future zero-copy `splice` can be added *behind the handle API*
  without changing one line of any program — that is what handles are for.
- **A bounded pipe is not a limitation — the bound IS the flow control.** A
  writer that fills the 64KB ring BLOCKS, which throttles the producer to
  exactly the consumer's speed and is the only reason a pipeline runs in
  constant memory. Do not "fix" this by growing the buffer on demand; an
  unbounded pipe is a memory leak with a friendly API. See `pipe.h`.
- **spawn does NOT blanket-inherit the parent's handle table** (Unix does). A
  child gets the console plus exactly the handles it was explicitly given.
  Deliberate: a child can never accidentally hold some unrelated pipe end open,
  which is a classic way pipelines hang. Do not "fix" this into Unix semantics.
- **Write atomicity is capacity-bounded, not `PIPE_BUF`-bounded.** os64's rule
  is one sentence — *a write of ≤ PIPE_CAPACITY lands whole, or it waits* —
  instead of Unix's magic 4096 constant that everyone has to memorize. Reads
  return SHORT and writes land WHOLE; the asymmetry is intentional (a reader
  that waits to fill its buffer deadlocks interactive pipelines; a writer that
  lands whole keeps records intact). See `pipe.h`.
