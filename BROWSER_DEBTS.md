# BROWSER_DEBTS.md — what the browsers owe, found by using them

DEBTS.md's shape, for the browser campaign: wend, yonder, and the
libraries under them (libhtml, libpage, libflow, libway, libfetch,
libimage). A row is something a person hit on a real page, or a known gap
with its trigger. What yonder's own design deliberately leaves for later
is booked in its constitution (`docs/design/completed/YONDER.md` § Booked);
this file is for what USE finds.

Each row names who owns the fix, because the browsers sit on libraries
with different owners and a finding in one is not a licence to edit
another.

## Open

| Debt | Found | Owner | What would pay it |
|---|---|---|---|
| **A window that wears no face draws a widget's non-ASCII text one byte per cell.** libui's fallback when no UI face is bound is the 8x16 bitmap cell, measured and drawn a byte at a time (`ui_font.c`), so a UTF-8 `é` in a yonder form field draws as two CP437 glyphs (`caf┬©`). What is SENT is right — httpbin echoed `café` — only the glass is wrong, and only in a window with no face. | 2026-09-26, Opus, in the guest: a form field holding `café`. | libui | Decode UTF-8 in the bitmap path, drawing each character the cell has and a marker for one it lacks, as the console's charset table does. |
| **A hop's Cookie and Referer lines get 1024 bytes between them.** libfetch hands `headers_for` a buffer of `OS64_FETCH_HOP_FIELDS_MAX` (`fetch.c`, `request_extras`), and the lines that say who is asking take up to `WAY_IDENTITY_MAX` of it first, which leaves the cookies and the Referer a kilobyte. A site's cookies pass that easily: a news site's analytics alone can, and Chrome sends up to 4096 bytes a cookie. libway fills that kilobyte with the cookies first, whole, and leaves the rest off, so a login still works when its cookie is among the first by path and age; when it is not, the site sees a stranger. | 2026-09-26, Opus, sizing yonder's jar (YONDER.md § Y3b). | Quinn (libfetch) | A `headers_for` buffer sized for the header a server will accept (8 KiB is where servers start refusing a request head), or the request built with the callback writing into the request itself. |
| **libgarb's numbers are not correctly rounded, and at the ends of a double's range that changes what they are.** The tokenizer scales a 19-digit mantissa by powers of ten it multiplies out (`consume_number`, `tokenize.c`), which lands within a few units in the last place: `1.7976931348623157e308` comes out Infinity where it rounds to DBL_MAX, `2.4703282292062328e-324` zero where it rounds to the smallest subnormal. The text as written is kept beside the value, so a serializer loses nothing; what reads the value sees the difference only in numbers no real stylesheet writes, and libflow saturates lengths far inside that range anyway. | 2026-09-28, Codex on the parser's review, past the dump's range check. | Opus (libgarb) | One correctly rounded decimal-to-binary64 for the browsers: libpage already carries one (musl's `decfloat`, `libpage/number.c`); hoisted where libgarb can link it, the tokenizer hands it the digits it read. |
| **A block-level picture that failed shows nothing where its alt text should be.** A page's sheet can make `img` a block (`img { display: block }` is in the common resets — Tailwind's preflight among them), and a block-level replaced box is laid out by its size alone (`layout.c`'s `block`, `FB_REPLACED`): `replaced_size` answers "lay out the alt text" for a picture that is not known and has one, which the INLINE path does (`text_segments`), but the block path has no line to put text on and lays out 0 by 0. A picture still arriving is 0 by 0 in the browsers too, and one that arrives, or whose size the page gave, is laid out right; the difference is only a picture that FAILED and has alt text — Chrome shows the alt there, yonder shows nothing. | 2026-09-29, Fable's hand-off on the cascade slice; confirmed on the flow slice, where the cascade first makes `img` block-level. | Opus (libflow) | A block-level replaced box that is laid out as its alt text gets a line of its own: the alt text shaped as an inline would be, the box as wide as that line (so `margin: 0 auto` still centres it) and one line high, with TEXT boxes under it that `flow_image` names as the picture's placement, as it does for an inline alt. Its own slice: the box tree has no block with an inline run it did not take from the document. |
| **A padding written as a calc() that works out negative is used negative.** A literal `padding: -4px` is refused by libgarb, but `calc(1px - 5px)` is valid, and Values 4 § 10.12 clamps it to 0 where it is used — Chrome computes `0px`. libflow resolves it to `-4px` and `len()` (`layout.c`) adds it to the box as it is, so the content moves out over the border. | 2026-10-03, Opus, auditing the class behind Codex's #208 round-2 finding (a negative calc() radius), with Chrome's computed values. | Opus (libflow) | Clamp padding to 0 where `len()` resolves it, every site that reads it (a percentage calc cannot be clamped before the box's width is known), with a cascade-to-layout case beside Chrome's answer. |
| **A zoom whose layout runs out of memory leaves the controls to lay their text out again.** yonder lends the controls the new zoom's face before laying the page out, because the layout measures a select in it, and lends the old face back when the layout fails (`lay_out_page`). The face comes back; the runs the controls had laid out in it do not, because a lend lets them go (`os64_ui_font_app`), so the next paint lays them out again, and under the same shortage draws them empty until memory comes back. | 2026-10-04, Codex on #215 round 5. | Opus (libui, yonder) | A staged lend, prepared beside the face in use and committed with the layout, or a select measured in the candidate set without lending it — so nothing the screen shows is let go before the layout that replaces it succeeds. |
| **A form control's furniture does not grow with the zoom.** yonder's controls are libui widgets, drawn in the Web face at the zoom — their text, and the box that text needs, scale — but the furniture around it is the widget's own, in device pixels: a listbox's 2 px frame, 8 px of row padding and 6 px label inset, a button's and a field's insets. At 200% a four-row select is `4 * (26 + 8) + 4` device pixels high where Chrome's would be twice `4 * (13 + 8) + 4`, because Chrome renders a control in CSS pixels, chrome and all. yonder sizes the box to what the widget draws (`select_size`), so the two agree; only the proportion differs. | 2026-10-04, Codex on #215 round 4. | Opus (libui, yonder) | A scale a window can give its app-face widgets — furniture in units of it, the way the face already carries the zoom — set by yonder at each zoom, and `select_size` measuring furniture in CSS pixels again. |
| **A web font's size refused for room twice draws in the fallback until the zoom or width changes, even after the room comes back.** A size whose open is refused for room (the tree on screen holds faces in the same budget) gets one more layout, and refused again its fallback stands until a layout refuses none or the page is laid out at another zoom or width (`webfonts_feed`). A new tree at the same zoom and width — a height-only resize, a script's rebuild — can be the one that lets the old tree's room go, but it starts no history over, so a size whose retry was spent before stays on the fallback. Only under text-memory pressure, only that size, and the next zoom or width change ends it. | 2026-10-16, Codex on #279 round 9. | Opus (yonder) | A retry history that starts over when a tree replaces the old one, except the tree a retry itself asked for — so it stays bounded — designed with the perf slice, because animation frames are such trees: a page that animates with a size refused for good must not lay out twice a frame. A host test of each: a height-only resize and a script's rebuild that free the room. |
| **The fonts record (S9a4) has four edges at its boundaries, one of which touches rendering.** (1) The resolver's `served` scratch for a list past 32 names is allocated whether or not a record is kept, so when memory is short a page with faces and such a list can fail a text run for the sake of record-keeping alone (introduced by #280 round 1, which sized it to the list). (2) A page whose first layout fails loses its face lines on its departure record: `page_lay_out` frees the cascade it built before `diag_leave` writes. (3) When the incomplete-layout retry frees the tree on screen and then fails too, `s_web.families`, `face_use` and `use_layout` still describe the freed tree. (4) A held file shared by a face that was used and one that was not, failing late, makes the unused face's next source read `not asked for yet` where it is `never asked for`. All four are memory- or room-pressure or narrow-sharing paths; (2)-(4) change only what the record says. | 2026-10-16, Codex on #280 round 10 (the last; Chris: book them). | Opus (yonder) | Slice S9a5, its own review: (1) first — the scratch only when a record is kept, or the run resolved without it and the census flagged; (2) the failed layout's faces written from its cascade before it is freed; (3) the published census let go, or flagged, when reclaim frees the tree it describes; (4) the late-failure reason only for a face whose own walk reached that source. Each a row in the lifecycle table of YONDER_DIAGNOSTICS.md § The page's fonts before code. |
| **A script's navigation inside a person's gesture is nobody's.** HTML gives `a.click()`, `form.submit()` or `location=` run by a listener during the person's click their activation (transient activation, read by "create navigation params by fetching"), so Chrome and Firefox send `Sec-Fetch-User: ?1`; yonder tracks no transient activation and sends none (`navigation_perform`, `WAY_BY_PAGE`). It under-claims, which is honest, but a gate that wants `?1` on a login form's scripted submit sees a bot | 2026-10-24, the W1 cold read | yonder (the script host's input path) | Transient activation: a person's input marks the window active for a short span, a navigation a script asks for inside it is a person's, and `?1` goes (DIVERGENCES row). |
| **The browser's Reload names no Referer.** Chrome 156 and Firefox 158 send the entry's own Referer again on Reload (capture-26-chrome-win-get-clicked, capture-43-firefox-linux-get-clicked), as they send its Sec-Fetch lines again; yonder's Reload replays the Sec-Fetch lines and names nothing (`trip_send`), though the page's `document.referrer` survives it | 2026-10-25, Opus, the W1 recapture | yonder (`trip_send`, `reload_as`) | The entry keeping its Referer beside its asking (`way_crumb_t.asked`), and the Reload sending it. |
| **A form's POST is ordered as a navigation, by guesswork it never made.** Each preset's navigation order (`agent.c`) comes from GETs; the W1 captures hold no form submission, so where Chrome and Firefox put a POST navigation's `Content-Length`, `Content-Type`, `Origin` and `Cache-Control` is not known, and those lines go after every named one in libfetch's order. A cookie's place is unknown the same way. | 2026-10-24, the W2 cold read | yonder (`agent.c`), with a capture | Capture a form POST first (`~/os64-opus-kit/w1/capture.py` can grow a form), and only then name those lines in each browser's navigation order; do not guess the order. |
